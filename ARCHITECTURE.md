# Architecture

## Status and units

This is the target design approved in Task #1. Task #27 (Movement v3, Task 1 of 4) replaced the earlier Movement implementation with a rewrite, Task #28 (Task 2 of 4) added speed-dependent powered turning, Task #29 (Task 3 of 4) added the retro-thruster capability, and Task #30 (Task 4 of 4) added the crew reaction delay; Task #41 compensated the arrival braking for the pilot response lag; Task #44 added the static-contact stop; Task #46 added hull-aware static navigation (one planning job per order, route guidance); Task #50 closed three false-safe paths in its prediction (corridor shortcut off the route, handoff from an unvalidated state, direct course); Task #48 widened the baked clearance into an ordinary-transit no-go zone (13.75 m agent radius), declines clicks inside it and rejects predicted maneuvers whose centre would enter it; Task #49 added the asteroid field (24 more copies of the asteroid in three clusters, one shared asteroid scene); Task #54 added destination resolution (a blocked or unreachable click resolves to the nearest suitable reachable point found by a bounded local search); Task #56 replaced the whole-flight maneuver search with path-first checked flight (one Godot path, a near-term safety and progress check every interval, corner clearance, distinct passages on demand, a blocked state, no planning brake); the actual inventory is listed below.

**1 world unit = 1 metre.** Gameplay movement is horizontal on Godot's X/Z plane. Ordinary movement does not chase Y; any later vertical animation belongs to the model only.

Data assets use m/s for speed, m/s² for acceleration, s for times, and metres for dimensions and distances. **Thrust units** are m/s² × the dimensionless gameplay mass divisor, so thrust / mass gives m/s². Angles are in degrees in data and debug output (radians internally). **Turn-authority units** are °/s² × the mass divisor, so turn_authority / mass gives °/s².

## Module map

| Module | Owns | May use | Status |

Movement is the only top-level gameplay module. Pilot guidance, propulsion and navigation are internal responsibilities, not independently exposed global modules. Task #46 returned path queries and route corners to Movement (Godot's `NavigationServer3D` and physics shape queries, both engine APIs); Task #54 added destination resolution inside the same planning job; Task #56 reads the baked navigation polygons through engine APIs for on-demand distinct passages (no second world graph is authored). Main owns the static navigation geometry (`NavigationRegion3D`). Scene-level mouse/camera input is composition glue, not a module.

Dependencies follow the one-way May-use map. Changes require an approved ticket stating the map change. Enforcement is review-only; no dependency tooling is installed or planned here.

## Movement boundary and authority

The command flow is caller → move-to or stop request → Movement's pilot → propulsion → authoritative ship transform.

- Movement alone writes the ship's authoritative transform and owns its heading and velocity. External callers request movement rather than writing transforms.
- Callers may read velocity and the read-only debug getters. No per-tick cross-system notifications are specified.
- Exact replacement, cancellation, arrival and failure notification semantics are **UNDECIDED** beyond the current behavior below. API signatures, state names, notification contracts, queues and hidden states are not prescribed.
- Movement does not call visual, input, UI or future gameplay systems. Other gameplay systems enter the dependency map only through later approved tickets.

## Earlier confirmed movement behavior

These owner decisions predate Movement v3. Task #28 superseded the near-opposite rule (no reversal threshold) and implements turning from rest only through speed (no turning at exactly zero speed); arrival ends commanded rotation. Task #46 applies the route-vertex rule below to its navigation routes. Whether each still applies is for the Movement v3 tickets (Tasks 15–17) and later ones to state:

- From rest, translation and turning begin together. Movement accommodates forward, backward, lateral and diagonal directions. Short journeys may end before the hull faces the destination.
- While moving, turns are relatively wide and momentum-aware; the ship follows a continuous trajectory.
- A near-opposite order (150°, relative to actual travel) brakes to rest before stationary movement begins.
- Arrival ends commanded rotation; there is no final alignment phase.
- Intermediate route vertices are not arrival targets; route following avoids stop/start, heading resets and jitter.

## Movement v3 (Tasks #27, #28, #29, #30, #41, #44, #46 and #56)

**Reaction delay (Task #30):** `move_to()` and `stop()` only *receive* a command. Each is appended to one per-ship FIFO queue with `due = received + reaction_delay` on Movement's physics clock (the sum of physics `delta`; input between ticks is stamped with the last tick's clock). At the start of each physics tick, before step 1, the clock advances and every command with `due ≤ clock` is activated in receipt order. A move then sets the destination, the order flag and the course heading from the ship's position **at activation**. A stop clears the order, so ordinary thrust-limited braking follows. Until then the active order (or idle braking) stands unchanged. A later command never cancels, merges with or reorders an earlier pending one, and stop has no bypass (owner: "Yes", issue #30). Commands due on the same tick are all applied in order, so the last one decides that tick. A delay of 0 activates on the next tick. Activation is quantized to the tick: with 60 Hz and float summation it lands 0 or 1 tick (≤ 16.7 ms) after the due time. Each receipt and activation is logged with `print()`.

Movement uses `CharacterBody3D` in floating mode with one `move_and_slide()` per physics tick and built-in physics interpolation. There is one world-space planar velocity (the built-in `velocity`, Y = 0) and one heading. No velocity channels are combined, no existing velocity is rotated, and there is no mode or phase state. The only rotational state is one per-ship turn rate and the current order's course heading; one more float, last tick's planar demand fraction, is kept for yaw-braking planning.

Each physics tick (everything read at the start of the tick, including the bow; turning demand is computed before the desired velocity, but the list keeps the propulsion order):

1. **Arrival:** an active order completes when the ship is within `arrival_tolerance` of its destination **and** its planar speed is at most `arrival_speed_tolerance`. Being inside the tolerance at higher speed is not arrival.
2. **Desired velocity** (arrival steering, Reynolds): with an active order, toward the destination at `clamp(sqrt(2 · a_plan · d) − a_plan · pilot_response_time, 0, max_speed)`. **Response-lag compensation (Task #41):** step 3 closes the gap through `pilot_response_time`, so the plain braking curve would leave the ship `a_plan · pilot_response_time` (3 m/s at 12 m/s²) too fast at the start of braking, crossing the destination and reversing; subtracting that lag makes the request exactly `−a_plan` while the ship is on the curve `sqrt(2 · a_plan · d)`. The desired speed is 0 within `a_plan · pilot_response_time² / 2` (0.375 m at 12 m/s²) of the destination, inside the arrival tolerance. No tuning value is added. Here `d` is the planar distance, `a_t = thruster_strength / mass` (the thrusters are the only brake) and **`a_plan = a_t / (1 + f_r)`**: the braking that proportional sharing leaves a saturated planar demand beside this tick's turning demand `f_r` (step 6), so 12 m/s² with no turn and 6 m/s² at full turn (owner-approved trial, PR #32). **Retro rule in planning (Task #29):** with `s = w · bow`, where `w` is the direction of the actual planar velocity (the direction to the destination only at exactly zero speed), `a_plan = min(a_t / (1 + f_r), L / s)` when `s > 0`; `L` is the sternward limit of step 7. With retro thrusters `L` is unlimited, so this is unchanged. Forward travel without retro plans at 5.4 m/s², sideways at 12, stern-first at 12. Without an order (after arrival or `stop()`) it is zero. It is never assigned to `velocity`. **Route guidance (Task #46):** a routed order replaces "toward the destination at distance `d`" with the guidance direction and the remaining path length, and caps the speed for each route corner ahead: `sqrt(a_b · R + 2 · a_b · d_corner) − a_b · pilot_response_time` with `a_b = min(a_plan, a_t / 2)` (the planar share proportional sharing leaves beside full turning demand) and the corner's guidance radius `R`. The direct order is unchanged.
3. **Requested acceleration:** `(desired − velocity) / pilot_response_time`.
4. **Main engine:** along the current bow only, `clamp(requested · bow, 0, main_acceleration)`. It is 0 whenever `velocity · bow < 0`, so it never reduces the current speed (non-negative work).
5. **Planar demand:** `t_req = requested − bow · main`, as a fraction `f_t = min(|t_req| / a_t, 1)`.
6. **Turning demand:** rated authority `α_max = (turn_authority / mass) × rudder_curve(speed / max_speed)` and turn-rate limit `ω_max = max_turn_rate_at_max_speed × rudder_curve(speed / max_speed) / rudder_curve(1)`, both from the **actual** start-of-tick speed (both 0 at rest only when the curve is 0 at speed 0; the owner's frigate curve is 0.05 there, so it turns slowly in place). The target is the order's **course heading**, set once when a move command activates, from the ship toward the destination (none for a zero-length order); positional correction after an overshoot never changes it, and a new order replaces it. With an active order, a course and `α_max > 0`, with the shortest error `e`, the wanted rate is `sign(e) · min(sqrt(2 · α_plan · |e|), |e| / delta, ω_max)` with **`α_plan = α_max / (1 + f_t_prev)`**, the turn's share if planar demand stays at last tick's fraction `f_t_prev` (owner-approved trial, PR #32; `f_t_prev` starts at 0 and carries over order replacement and `stop()`, since it measures actual thruster demand) (braking-distance rule; the `|e| / delta` term is only a numerical aid, and the heading can still cross the target). The request `α_req = (wanted − rate) / delta` gives `f_r = min(|α_req| / α_max, 1)`. Otherwise `f_r = 0` and the turn rate is set to 0: rotation does not persist without powered turning (intentional non-Newtonian rule).
7. **Shared capacity:** if `f_t + f_r > 1`, both are scaled by `1 / (f_t + f_r)` (owner-approved proportional sharing). At full demand on both, the thrusters give 6 m/s² and turning half its rated authority. The main engine is outside this capacity. **Retro rule (Task #29):** when `retro_thrusters` is false, the thruster command's component toward the stern (along −bow) may not exceed `L = no_retro_braking_effectiveness × a_t` (5.4 m/s²). After sharing, only the excess sternward part is removed: lateral and bow-forward parts are untouched, nothing is scaled up and the removed capacity is not reallocated (to turning either). The turning and planar fractions are computed before the cap. It applies to all sternward thrust: braking a bow-first motion and accelerating stern-first (owner-provisional, "Yes I agree until I see it").
8. **Integration:** `rate = clamp(rate + α · delta, −ω_max, ω_max)` (when the limit contracts faster than the authority can slow the turn, the rate is clamped, never the heading); `velocity += (bow · main + thrusters) · delta`, planar magnitude hard-clamped to `max_speed`; `yaw += rate · delta`; then `move_and_slide()`.

Yaw never rotates the velocity. The speed-linked rate limit is the only yaw-rate cap (owner-approved trial, PR #32); there is no heading snap or final alignment. There is no position hold, snap or speed reset: after arrival or `stop()` the ship brakes toward zero velocity wherever it is. A small overshoot at low speed can still occur (the destination is passed below the arrival speed and the ship rests just past it); a genuine miss is corrected normally.

**Static contact (Task #44):** right after `move_and_slide()`, each slide collision is checked. It qualifies when the collider is a `StaticBody3D` but not an `AnimatableBody3D`, and this tick's attempted planar velocity (before the slide) has a negative dot product with the collision normal's XZ projection (driving into the surface; glancing contact included). On the first qualifying collision the active order ends (the pending queue is untouched, `stop()` is not used), `velocity` and the turn rate become 0, the position stays where the engine left it, and one line is logged. It applies with or without an active order (coasting or braking). Resting or outward contact never qualifies, so an order away from a touching obstacle proceeds. No state, getter, signal or tuning value was added. Contact with any other body type keeps Godot's default sliding; no hard-stop rule is promised for it.

## Navigation (Tasks #46, #48, #50, #54 and #56)

**No-go zone (Task #48, owner Option A):** the baked mesh's exclusion around an obstacle (agent radius 13.75 m, so 19.75 m from the 6 m sphere's centre on its axes) is the static no-go zone for ordinary transit, defined for the ship's **centre**: routes run outside it, clicks inside it are resolved to a point outside it (Task #54; declined by Task #48 before), and a predicted maneuver whose centre would go more than `no_go_tolerance` beyond the mesh edge is rejected. The rotating hull may extend into the zone; only the physical obstacle may never be touched. It is a planning rule, not a physical boundary: no wall, snap or steering force. Fast-path routes (no hazard, from rest or with a clear drift corridor) are not checked; the pilot's lookahead can cut the hole's polygon corners by up to about 0.5 m (measured).

Each activated move starts **one navigation job** (`Navigator`) that lives as long as the order. From activation the ship **coasts** (`ShipPilot.Targets.coast`: no thrust and no commanded turning; the velocity carries over and rotation stops), so the previous order's steering is gone at once but its momentum is not braked away; `has_order()` stays true and `is_planning()` reports the route phase. Path-first (Task #56, owner-approved redesign): the job asks Godot for **one ordinary path**; an open-space route is handed to the pilot once and flown unchecked as before; a route near obstacles is flown under **checked flight**, where the job decides every interval what the ship does and may switch to a **distinct passage** when the path cannot be negotiated. Task #46's "one plan per order, never re-planned" is replaced for this scope (owner decision on #56): targeted replanning happens only when the current path is rejected. A later move or stop activating cancels the job, its checks and any query; its work is never applied. The FIFO due times are unchanged.

- **Scheduling:** jobs of all ships share one wall-clock allowance per physics tick (`NavigationBudget.plan_time_per_tick`), served oldest first; a job only waiting (for navigation to sync, or a guiding job whose next decision is ready) does not hold up the others. All work runs in small items (one readiness check, one classification, one path query with route cleanup, one route sample, one corridor sample, one corner sample, one A* expansion, one predicted tick whose hull check covers at most 16 ticks); a `PlanClock` starts an item only if it can end before the deadline at the longest item duration measured so far (held back at most half the allowance). Unfinished work continues on the next tick. In checked flight a decision that is not ready at its interval boundary makes the ship brake for that interval (the conservative fallback); otherwise the allowance only spreads work. A single unobstructed order finishes in its activation tick, so its flight is bit-identical to the pre-Task #46 direct order.
- **Readiness:** map inactive or iteration 0, or an enabled region with region iteration 0: wait (no path query). No enabled region once the map has synced: navigation unavailable. Regions synced but no polygon merged (no closest-point owner): wait while the map iteration still changes; after `MERGE_WAIT_FRAMES` (2) frames without change, unavailable.
- **Classification:** navigation unavailable, or a click outside every enabled region's XZ bounds (the region bounds equal the mesh AABB, verified), keep the **direct order (baseline)**, logged. A click inside the bounds but more than one map cell (0.25 m) from the mesh lies in a no-go zone and is **resolved** (Task #54, below; Task #48 declined it). An empty path, or a path whose end does not reach the click along a straight leg that stays on the mesh (sampled every cell), also starts resolution. Godot can end a path short of an on-mesh target (observed: (97.43, −12.02) for a click on (98, −12), 0.57 m away); the route then ends with that leg. Otherwise the route is the ship, the path corners and the click or resolved destination (Y at the ship; a path start within one cell of the ship is the ship; corners within one cell of the line between their neighbours are dropped).
- **Destination resolution (Task #54):** a click inside the regions' bounds that is off the mesh (a no-go zone) or that the path cannot reach is replaced, within the same planning job, by the nearest candidate found by a bounded local search; a valid click is unchanged and makes no extra query. All of it is `RoutePlanner` work items inside the shared per-tick allowance; a later command cancels it.
  - **Candidates:** one queue sorted by planar distance from the requested click: C0 (the mesh point nearest the click), the end of every failed candidate path (Godot's nearest reachable point to that candidate) and probe points on rings of `RING_DIRECTIONS` (8) around the click at radius `s · 2^(k−1)` (`s` = hull reach + `plan_clearance_buffer`, 11.18 m for the frigate; alternate rings turned 22.5°), each projected with `map_get_closest_point`. Ring points are generated one per item, only while the queue is empty or its nearest candidate is not nearer than that ring's radius (less one cell), so a ring is complete before anything at its radius is tested; rings stop after the first one whose radius covers the farthest corner of the enabled regions' bounds (the horizon). A projected ring point can land nearer than its ring's radius and is then tested after farther points of earlier rings (accepted approximation). A candidate whose projection moved more than one cell is moved onto the mesh by the arrival allowance `A` along the projection; candidates within one cell of an earlier one are dropped.
  - **Tests (nearest first):** the arrival allowance: the candidate and 8 points on its radius-`A` circle each within `no_go_tolerance` of the mesh, and a cylinder of hull reach + `plan_clearance_buffer` + `A` free (hull clear at any yaw wherever it can rest); then, as its own item, one path query from the ship with the on-mesh leg rule, counted against `NavigationBudget.destination_candidates_per_order`. The first candidate the path reaches is the destination: the route then runs to it unchanged (fast path or checked flight). A failed path adds its end as a candidate.
  - **Arrival allowance:** `A = arrival_tolerance + arrival_speed_tolerance² / (2 · a_min)`, `a_min = a_t / 2` (or the no-retro cap when lower): a resolved order completes within `arrival_tolerance` at no more than `arrival_speed_tolerance` and then only brakes, so it rests within `A` (2.08 m for the frigate). It bounds the resting position, not a genuine miss that passes the circle faster; the 8-point circle is a conservative approximation, not a proof.
  - **Outcomes:** a candidate is rejected as unreachable from the ship (path ends elsewhere), no arrival allowance, hull does not fit or no path. An order is declined as **destination search exhausted** (the path-test bound used up, candidates left) or **no destination found in bounded search** (queue empty at the horizon); neither claims physical impossibility. Checked flight never tries another destination (an unresolved approach is **blocked**, below).
  - **Evidence:** the plan log lists the summary, every tested candidate in test order with its outcome, and the closest-point, path and physics query counts; F3 shows the requested click and the resolved destination as text.
- **Hazard scan:** route samples every hull half-width; the first one where a cylinder of radius hull reach + `plan_clearance_buffer` around the root is not empty (the hull might touch something there at some yaw) ends the scan: the route needs checked flight.
- **Drift corridor:** a ship moving at `v` can drift sideways off the route by at most `v² / a_t` (its braking distance at the planar share left beside full turning, `a_t / 2`). The corridor is clear when the ship's position and every route sample ahead have an empty cylinder of radius hull reach + buffer + `v² / a_t`.
- **Fast path:** no hazard sample and the ship at rest or its drift corridor clear: the route (or the direct order for a 2-point route) is handed to the pilot once and flown unchecked.
- **Checked flight (Task #56):** otherwise the job decides, for every interval of `pilot_response_time` (I = 15 ticks at 60 Hz), what the ship does in the next one: **follow** its route, **brake** (the pilot without an order) or, only after activation, **coast**. Each decision is computed during the interval before it, from the predicted state at its start (the boundary), and adopted at the boundary only if the ship's actual state equals the prediction (`Navigator.HANDOFF_TOLERANCE`, 1e-3 summed over position, velocity, yaw and turn rate; float noise only: Task #50 measured 0–1e-7 while braking, Task #56 measured 2e-4 to 4e-4 in the arrival approach, where the speed law's square root amplifies noise). Otherwise, or when the decision is not ready, the ship brakes for that interval and the next decision starts from its actual state. Navigation never commands thrust: it only selects the guidance, and `ShipMovement` turns it into pilot targets.
- **Activation:** the ship coasts for `ACTIVATION_INTERVALS` (2) intervals, 0.5 s for the frigate. The job's first work after the route query checks that coast followed by braking to rest from the **live** state (hull and no-go); if the coast itself would touch something or breach the no-go rule, the ship brakes at once. The first decision is taken for the end of the coast. Two intervals, not one, because the first decision of a moving redirect (route, corners, an alternative-passage query and its checks) needs about 21 ms of work, 17–18 ticks of the shared allowance (A2 measurement); a late first decision would brake the ship.
- **Decision order (all predictions from the boundary state with the real pilot, guidance and hull and the no-go rule; `ManeuverCheck`):**
  1. **Safety:** follow the route for one interval, then brake to rest: clear. **Progress:** follow the route for the window `W = speed / a_b + pilot_response_time` (`a_b` the weakest planned braking, 1.67 m/s² for the frigate; 5.9 s at 9.5 m/s): no contact and no no-go breach. Both pass: follow.
  2. **Slowing (not for the first decision after activation):** brake if braking 1, 2, 4, … intervals, with the ship still above `arrival_speed_tolerance`, makes the progress window pass.
  3. **Alternative passage:** while `NavigationBudget.path_recoveries_per_order` allows, a `PassageGraph` query from the boundary position to the same destination; the first distinct route (corners shaped) whose safety and progress checks pass is followed. A query counts when its decision is adopted.
  4. Follow the route if its safety check passed (safe for one interval, re-checked next).
  5. Brake. When the ship is at or below `arrival_speed_tolerance`, nothing passes and no query is left, the order is **blocked (unresolved)**.
- **Why braking is safe:** every adopted follow interval was checked with its brake-to-rest tail, and braking continues exactly that tail. After a late or mismatched boundary, or when the activation coast's braking was not proven, the brake is the best physical response but not proven; collision avoidance is not claimed when the ship cannot stop in time, and Task #44's contact stop remains the last safeguard.
- **Corner clearance (`PassageGraph.CornerShaper`):** before a route is checked or flown, each interior corner where it turns by more than about 1° is moved outward along its bisector, away from the obstacle the route bends around, by `MovementProfile.path_corner_clearance` (route corners lie on the mesh edge, which the lookahead aim cuts). Both legs into and out of the moved corner must stay on the mesh (sampled every 0.5 m within one cell), otherwise the offset is halved; below 0.1 m the corner stays. A moved corner therefore never pushes a leg out of a narrow passage further along it.
- **Distinct passages (`PassageGraph`, on demand only):** the polygons of the map's single enabled navigation region, read through engine APIs (`map_get_regions` → `region_get_owner_id` → the region's `navigation_mesh`, `region_get_transform`) into a read-only cache shared by all ships, built in items of 16 polygons and rebuilt when the map iteration changes. Two polygons sharing an edge are adjacent through that portal. A query runs A* over polygons (cost: distance between portal midpoints times the portal's penalty; straight-line heuristic; binary heap), a funnel turns the portals into corners, and the portals used cost ×4 for the next search (search-shape constant). A route whose every point lies within `detour_lookahead_distance` of a rejected or earlier route is the same passage and skipped. Routes come in generation order (no ranking), at most `NavigationBudget.passage_searches_per_query` searches per query. A map with more than one enabled region has no alternatives (portals between regions are not represented).
- **Blocked (unresolved):** the order stays active (`has_order()` true, destination kept, F3 "blocked"), the ship brakes to rest, and nothing is searched again; the next activated command supersedes it. It never claims the destination is unreachable.
- **Guidance (per tick, real flight and prediction alike):** route progress advances past a corner when the ship crosses that corner's bisector. The pilot aims `detour_lookahead_distance` ahead along the route, the course heading follows that aim, the speed law uses the remaining path length, and each corner ahead caps the speed (step 2). Corner radius: the smaller of `lookahead / (2 sin(turn / 2))` and `(incoming + outgoing segment length) / (2 · turn)`. When the aim reaches the destination, the final approach is the ordinary direct arrival with the course frozen at the hull's yaw then (no turning left to share the thrusters with braking; no final alignment).
- **No-go check (Task #48):** each predicted tick queries the map's closest point to the predicted centre. Once the centre has been within `no_go_tolerance` of the mesh (from the start) or within one map cell (later), a tick more than `no_go_tolerance` beyond it fails the prediction ("centre enters the no-go zone at (x, z)"); a ship starting deeper inside a zone may leave it.
- **Hull test (`HullProbe`):** the box from the ship's own `CollisionShape3D`, at predicted planar poses (overlap: `intersect_shape`; sweep: `cast_motion`; both with the ship's collision mask, excluding the ship). A tick is clear when the exact hull at its first pose does not overlap (only for the first pose of a prediction; later poses lie inside the previous tick's sweep), a yaw change's hull grown by `reach · |Δyaw|` does not overlap, and that hull swept along the translation is free. So a touching ship may translate away but cannot rotate a corner inward. A segment of ticks is first tested once with the hull grown by its whole motion bound (`Σ|Δp| + reach · Σ|Δyaw|`, closing at one hull half-width); an overlap halves it down to single ticks. Conservative for geometry that is static while the plan is made; not a proof for moving bodies.
- **Contact:** contact still ends the order under Task #44.

## Reusable ship composition

The reusable ship scene `Ships/ship.tscn` separates authoritative movement from a visual/model child `Visual` (a plain `Node3D` wrapper). Only that child may ever tilt visually; the authoritative root and collision never tilt.

Banking is **deferred**: Task #27 deleted the former `ShipVisualBank` script and `ShipBankProfile` resource, since they read Movement's removed API (Git history, `main` at a174d22).

Shared function and appearance use one authoritative scene/script/resource. Ship differences use configuration rather than duplicated implementations; check existing assets before creating another shared definition. Per-instance runtime state must not modify shared resources.

The owner's placeholder is `Assets/Ships/Whitebox/Arrata_Frigate_001.glb`. Preserve the source unchanged, including its scale and pivot; import metadata is asset metadata, not a movement design decision.

## Data and validation

Per-ship tuning belongs in Godot `Resource` data assets, not code constants. Shared assets hold configuration only; runtime state belongs to the individual ship. Each tunable requires a default, unit and owner-approved range. `MovementProfile` holds the provisional values (see the inventory). Start conservatively and adjust in play.

The first playable work uses one ship in open space in the developing game scene, rather than multiple test scenes. The intended battle scale is tens of units; assess it with real combat later, without treating that intention as a measured performance target.

The rejected upfront alternative is a global command/orchestration framework, an independently deployable navigation system and custom simulation. They add coupling and complexity before confirmed users require them.
