# Architecture

1. **Map and group the current system.** Catalogue active modules and meaningful internal responsibilities, their dependencies and connections to the wider project. Group where it clarifies existing architectural boundaries; distinguish modules from scene composition and implementation helpers.

2. **Document interfaces.** Describe what each module provides, consumes and controls, including ownership and dependency direction. Include only contracts another component must rely on or respect. Retain necessary distinctions in command activation, cancellation, failure handling and fallback behavior; avoid exhaustive API inventories.

3. **Keep it minimal and current.** Update existing entries instead of appending explanations; add entries for genuinely new responsibilities and remove obsolete information. Exclude low-level algorithms, numeric tuning, implementation walkthroughs, history and test records. Retain units, coordinate conventions, configuration ownership and useful source links. Verify claims against current code and report substantive conflicts with approved decisions for owner review.

## System map

| Boundary | Owns | Dependencies |
|---|---|---|

| [Camera](game/camera/camera_rig.tscn) | Floor focus, view transform and camera input | Shared camera settings; Godot only |
| [Ship presentation](game/presentation/ship_selection/ship_command_presentation.tscn) | Selection ring, destination marker and straight connector | Orders' latest receipt and pending point; Movement's planning and accepted destination observations; Fleet's fleet-order click; shared presentation style; Godot |
| [Debugging](debugging/debugging_suite.tscn) | F4 diagnostic stop, F7 crossing orders, arrow-key diagnostic propulsion, telemetry display and diagnostic visuals for the current selection; the [traffic scenario scene](debugging/scenarios/traffic_scenario.tscn) and its setups | Fleet selection and roster; Orders commands and queue observations; Movement read-only observations and its diagnostic propulsion command; injected scene references; shared ship, camera, Fleet and asteroid scenes; Godot |
| [Display and UI configuration](project.godot) | Window/reference sizing and proportional UI scaling; shared UI theme | Godot; shared [theme resource](game/ui/ui_theme.tres) |

Movement and Camera are independent gameplay modules. Command lives outside Movement in two modules: Fleet → Orders → Movement. Fleet also reads Movement and drives ship presentation selection; presentation reads Orders; Debugging reads Fleet and Orders and sends Movement its diagnostic propulsion command. Movement never depends on Orders, Fleet, Camera or Debugging. Main and Ship are composition boundaries. New module dependencies require an approved ticket stating the map change.

**Physics tick order:** every ship's Orders (`process_physics_priority = -20`) advances its clock and activates due commands in receipt order; Debugging (priority -10) sends the diagnostic propulsion command; then each ship's Movement (priority 0) runs, the first one servicing Navigator and then the traffic pass (once per frame, before any ship moves); diagnostic trails sample afterwards. The traffic scenario root issues its timed orders at priority -30.

**Physics layers** (bitmask = `1 << (layer − 1)`, names in Project Settings): layer 1 static obstacles; layer 2 navigation floor (layer `2`, mask `0`); layer 3 ships (layer `4`, mask `5`: obstacles and ships). Static navigation in `HullProbe` queries only layer 1 (`STATIC_OBSTACLE_MASK`), so it never sees ships; only ship traffic checks query layer 3 (`SHIP_MASK`). Selection picking uses the default ray mask.

Main supplies the navigation map through Godot's `NavigationRegion3D` and physics geometry. Static obstacle instances share [one scene](Main/asteroid.tscn); geometry changes require rebaking the navigation mesh. The navigation floor is bake geometry and is excluded from the ship's physical collision mask.

The ship's collision shape is navigation's authoritative hull source; hull queries currently support boxes. Visual presentation belongs under `Visual` and must not tilt the movement root or collision hull. Preserve the imported model's source, scale and pivot.

## Movement

### External contract

- Only Orders calls `activate_move(world_position, receipt)` and `activate_stop()`; Movement has no command queue, delay or immediate-execution path. Activation replaces the active order and cancels its navigation work without changing position, velocity, heading or turn rate. Destination Y is ignored. `get_planning_move_destination(receipt)` exposes the requested point while that active move is initially planning. `get_resolved_move_destination(receipt)` exposes the destination while the move is active and accepted. `set_traffic_slot(i)` stores Fleet's roster index. `get_reservation_radius()` (metres), `get_stopping_point()` (planar, metres), `get_remaining_path()` (the route from the ship), `get_predicted_path()` (currently the remaining path), `is_blocked()` (always false) and `get_traffic_status()` (always open) are read-only observations. `contact_stop(other)` is called only by another ship's Movement on contact.
- Only Debugging calls `set_diagnostic_propulsion(main, retro, rcs)` (main and retro 0–1, RCS −1 right to 1 left). It is a diagnostic control, not a player control; it applies while any part is non-zero.
- `ShipMovement` alone applies authoritative motion through the character body. Read-only observations expose commands, requested/resolved destination, status and telemetry; there are no movement notification signals. Invalid movement configuration disables motion.
- **V4 experiment (`V4-Movement-design`, #102):** there is no pilot. A move is planned and stays active until a new move or stop replaces it; nothing completes it by arrival, and no order commands propulsion. A stop ends the active order without braking. Driving into a stationary static obstacle ends the active order and zeroes motion; driving into another ship does the same to both ships in the same tick and releases both reservations. Pending commands survive.

### Internal responsibilities

**Controller — [ShipMovement](Movement/ship_movement.gd).** Owns command/order lifecycle, live motion and route progress. It supplies the propulsion command (the diagnostic command, otherwise none), applies the result and handles collision stops. Planning reads live state through `get_propulsion_state()`.

**Propulsion — [ShipPropulsion](Movement/propulsion.gd).** One pure step: main engines along the bow, retro thrusters toward the stern, RCS rotation. Each has its own capacity; none shares a budget or pushes the ship sideways. Velocity changes only by applied main/retro thrust; rotation never rotates, damps or clamps it. Speed limits restrict thrust along the hull axis (main to `max_speed` forward, retro to `max_reverse_speed` toward the stern), never velocity, so drift plus thrust can exceed `max_speed`. RCS builds turn rate up to the turn-rate limit while commanded; on release, and on a direct reversal before building the other way, it brakes the rotation with the same authority until the hull stops (owner, Option C). A rate above a limit that contracted with speed is braked down to it. Rotation never jumps or spins freely. It never moves scene objects or advances position.

**Navigation — [Movement/Navigation](Movement/Navigation/).** Supplies routes and endpoint decisions to the controller. In the V4 experiment nothing steers along a route, and stopping estimates are provisional compatibility calculations (`HullProbe.minimum_braking()`: the weaker of main and retro, turning time excluded), not the V4 stopping model.

- **Routes:** `Navigator` manages jobs/cancellation; `RoutePlanner` acquires Godot paths and resolves unsuitable or reserved points through bounded search, never farther than the shared destination limit from the requested point (0 = no additional limit). `RouteGuidance` holds plans and tracks per-ship progress along them.
- **Clearance:** `HullProbe` queries the real hull, static space and navigation boundaries for planning and traffic. Physical hull clearance and the navigation mesh's centre no-go constraint are separate requirements. None of these helpers writes live motion.
- **Endpoint reservations:** [`EndpointReservations`](Movement/Navigation/endpoint_reservations.gd) is a static registry per navigation map covering every ship. Its area is a disk of hull reach + clearance buffer + arrival allowance. An accepted order reserves its endpoint when its job finishes, so jobs finishing in the same service call see it; activation (move or stop), removal and static or ship contact release it. A ship without an order occupies its live position; a planning ship occupies nothing. Destination resolution treats another ship's area as unavailable.
- **Ship traffic:** [`Traffic`](Movement/Navigation/traffic.gd) is a static coordinator per navigation map. It still snapshots ships and computes its decisions once per frame, but in the V4 experiment Movement does not apply them (no pilot to yield, hold or reposition). Contact remains the fallback.
- **Work ownership:** `Navigator.service()` runs once per physics frame and bounds shared planning work across ships with `PlanClock` item counts from the budget (route work and boundary preparation separately), never by measured time; unfinished work continues next frame. Measured time is telemetry only. Boundary caches are shared per map, invalidated by map iteration changes and released when its last ship leaves.

A direct plan (straight line, static-contact fallback) is selected only for no enabled navigation regions, no navigation polygons after synchronization checks, or a requested destination outside every enabled region's bounds. An inactive or unsynchronized map leaves the route job pending, with live clearance still checked. Pathfinding or destination-search failure does not select this fallback.

## Camera

[CameraRig](game/camera/camera_rig.gd) owns a horizontal floor focus and its child Camera3D. Zoom and yaw orbit preserve that focus at screen center; camera-relative panning translates it. Only the active camera accepts unhandled input, and held controls clear on window focus loss or deactivation. Removing Debugging leaves camera controls available.

Levels instance the master scene and place its root at their initial floor focus. The shared [settings resource](game/camera/camera_settings.tres) is Inspector-editable and read-only at runtime; local tuning copies/overrides are avoided so master changes propagate. View and input state belong to each rig. Pan speed scales with current smoothed height relative to the configured starting height. Input bindings belong to Project Settings' Input Map.

Consumers obtain Camera3D through `get_camera()`; `set_view(focus_position, height, yaw_degrees)` immediately places the view and synchronizes zoom within its limits. Focus Y defines the camera's floor elevation; this does not change Movement's X/Z gameplay plane.

## Orders, Fleet and ship presentation

[ShipOrders](game/command/orders/ship_orders.gd) is the sole authority for receiving and delaying commands. Each ship instances it as `%Orders`. `move(point)` returns a per-ship receipt; `stop()` is delayed like a move, with no bypass. Every command waits the shared [crew profile](game/command/orders/crew_profile.gd)'s delay on Orders' own physics clock, then activates in receipt order; nothing is cancelled or skipped. Orders exposes its clock, queue, last receipt/activation times, latest receipt and pending points, and logs every receipt and activation.

One [FleetCommand](game/command/fleet/fleet_command.gd) per playable viewport owns the roster (slot order middle, left, right) and an ordered selection (`get_selection()`, roster order). Input Map actions `select_fleet` and `select_ship_1..3` select the roster or one slot; a missing slot does nothing. It processes unhandled clicks in input order: the physics-space pick selects one roster ship or clears the selection. A right-click projected onto Y = 0 is dispatched immediately when no pick is pending. One selected ship receives the click. Several each receive a preferred point spread across the travel direction (from their centroid to the click), in the left-to-right order of their stopping points (`get_stopping_point()`: where each would come to rest braking straight from its velocity; its position at rest), twice the largest reservation radius apart. Fleet sets each presentation's selected and fleet-order state and shows one shared pending marker (the [move feedback](game/presentation/movement/move_feedback.tscn) glyph, without connector) at the click while any ship of that order is pending in Orders or planning in Movement and one of them is selected.

Each ship instances [command presentation](game/presentation/ship_selection/ship_command_presentation.tscn) under `Visual`. Each selected ship displays only its latest Orders receipt. Blue feedback marks the requested point during the reaction delay and initial planning; for a fleet-order move the ship hides its own glyph and draws its connector to the fleet's click. Gray feedback marks the accepted endpoint. All feedback is flat horizontal geometry in world metres at Y = 0, built by one shared [ring builder](game/presentation/ground_feedback_mesh.gd). The selection ring follows the ship's rendered X/Z position. The destination glyph stays at the destination and turns about Y so its outer arc faces the rendered ship position. The connector runs between the selection ring and the outer destination radius, leaving a world gap at each end, and hides when there is no room for both gaps. World depth applies to all feedback. Deselecting hides it. The [preview](game/presentation/movement/move_feedback_preview.tscn) uses the production Fleet (two-ship roster), camera and ship scenes.

## Debugging integration

[DebuggingSuite](debugging/debugging_suite.gd) receives the fleet, collision shapes and reference positions from its host and follows the fleet's selection each frame. Removing it cleans up generated outlines attached to external collision shapes.

F4 queues a diagnostic stop through Orders on every selected ship. Each physics frame the suite reads the Input Map actions `debug_main_thrust` (Up), `debug_retro_thrust` (Down), `debug_rcs_left` (Left) and `debug_rcs_right` (Right) and sends them to every selected ship's `set_diagnostic_propulsion()`, and zero to every other roster ship. F7 queues the three crossing orders through the roster ships' Orders (valid only in a fresh run; F3 then says so). Every F3 block includes the ship's traffic status. The [traffic scenario scene](debugging/scenarios/traffic_scenario.tscn) instances the production ship (×3), camera, Fleet and suite, adds asteroids per setup, and has no navigation mesh (direct mode); each [`TrafficSetup`](debugging/scenarios/traffic_setup.gd) resource under `debugging/scenarios/setups/` holds start poses, per-instance test profiles (copies, never the shared profile), timed orders and asteroids, selected on the scene root and run with F6. F3 shows the full readout for one selected ship, one compact block per selected ship in roster order for several, or "no ship selected". The suite makes one trail per roster ship from its `MovementTrail` node; F3 shows the selected ships' trails, restarting a trail when its ship becomes selected. Trails sample actual world positions after movement. Shared visual definitions and settings remain reusable; runtime state belongs to each suite.

The suite owns the overlay's scene-based Control layout, margins and wrapping telemetry label. Diagnostic Controls ignore mouse input. The label selects the shared theme's `DebuggerLabel` variation; its outline does not apply to ordinary UI labels. On initialization and viewport resize, the overlay caps its label's nominal screen-pixel font size using that variation's limit and the actual viewport stretch, rounding down. The font override belongs to the label instance; the shared theme and ordinary UI scaling remain unchanged.

## Display and UI configuration

[Project settings](project.godot) own the logical UI reference and independent initial window size. Canvas-item stretching scales UI proportionally; expand aspect handling adds logical space for other aspect ratios. Startup is resizable and windowed, with no enforced minimum size. The 3D view renders at the window resolution; Camera does not own display configuration.

The external [UI theme](game/ui/ui_theme.tres) supplies the project-wide default font size and the opt-in debugger outline variation. Shared theme data is read-only at runtime. Layout dimensions belong to reusable scene resources. Godot's embedded-game sizing remains an editor preference, separate from project window/scaling settings.

## Data and units

Shared Godot Resources hold configuration and are not mutated per instance. Orders, motion and route progress belong to each ship. Tuning values belong in data assets, with defaults, units and approved ranges defined by their resource scripts:

- [MovementProfile](Movement/movement_profile.gd) defines movement configuration: main and retro acceleration, forward and reverse speed limits, the RCS turn-acceleration and turn-rate curves, and the navigation values; the [frigate resource](Movement/Profiles/frigate_movement_profile.tres) supplies the active hull's values and curves.
- [CrewProfile](game/command/orders/crew_profile.gd) and the [veteran crew resource](game/command/orders/veteran_crew.tres) define the command reaction delay.
- [NavigationBudget](Movement/Navigation/navigation_budget.gd) and its [resource](Movement/Navigation/navigation_budget.tres) configure shared navigation limits, including the destination limit.
- [Trail settings](debugging/movement_trail_settings.gd) and their [resource](debugging/movement_trail_settings.tres) configure diagnostic sampling.
- [Ship feedback style](game/presentation/ship_feedback_style.tres) configures shared materials and all feedback sizes in world metres: selection and destination radii and strokes, connector width and gaps.
- [Camera settings](game/camera/camera_settings.gd) and their [resource](game/camera/camera_settings.tres) configure view, zoom, orbit and pan behavior.

One world unit is one metre. Gameplay motion uses world X/Z; the bow points along local -Z. Speed uses m/s, acceleration m/s², distances metres and durations seconds. Angles use degrees in data/debug output and radians internally; angular acceleration/rate use °/s² and °/s in data. Main, retro and RCS capabilities are specified directly as accelerations; there is no mass value.
