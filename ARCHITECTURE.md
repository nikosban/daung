# Architecture

## Status and units

This is the target design approved in Task #1. Task #27 (Movement v3, Task 1 of 4) replaced the earlier Movement implementation with a rewrite, Task #28 (Task 2 of 4) added speed-dependent powered turning, Task #29 (Task 3 of 4) added the retro-thruster capability, and Task #30 (Task 4 of 4) added the crew reaction delay; Task #41 compensated the arrival braking for the pilot response lag; Task #44 added the static-contact stop; Task #46 added hull-aware static navigation (one planning job per order, route guidance); Task #50 closed three false-safe paths in its prediction (corridor shortcut off the route, handoff from an unvalidated state, direct course); Task #48 widened the baked clearance into an ordinary-transit no-go zone (13.75 m agent radius), declines clicks inside it and rejects predicted maneuvers whose centre would enter it; Task #49 added the asteroid field (24 more copies of the asteroid in three clusters, one shared asteroid scene); Task #54 added destination resolution (a blocked or unreachable click resolves to the nearest suitable reachable point found by a bounded local search); the speed-dependent directional-thrust task (branch `orientation`) made the directional thrusters' sideways and bow-forward acceleration fade with actual speed, and the follow-up made the main engine the primary forward propulsion (a separate, smaller bow-forward directional limit); bow alignment then limited the steering target to a speed-dependent angle from the travel direction; speed-dependent turning then replaced the rising rudder curve with turning-acceleration and turn-rate curves that peak at low speed; Task #60 replaces whole-flight approval with responsive route guidance and local physical clearance; the actual inventory is listed below.

**1 world unit = 1 metre.** Gameplay movement is horizontal on Godot's X/Z plane. Ordinary movement does not chase Y; any later vertical animation belongs to the model only.

Data assets use m/s for speed, m/s² for acceleration, s for times, and metres for dimensions and distances. **Thrust units** are m/s² × the dimensionless gameplay mass divisor, so thrust / mass gives m/s². Angles are in degrees in data and debug output (radians internally). Turning acceleration is in °/s² and turn rate in °/s, both directly (not divided by mass).

Movement is the only top-level gameplay module. Pilot guidance, propulsion and navigation are internal responsibilities, not independently exposed global modules. Dependencies follow the one-way May-use map. Changes require an approved ticket stating the map change. Enforcement is review-only; no dependency tooling is installed or planned here.

## Movement boundary and authority

The command flow is caller → move-to or stop request → Movement's pilot → propulsion → authoritative ship transform.

- Movement alone writes the ship's authoritative transform and owns its heading and velocity. External callers request movement rather than writing transforms.
- Callers may read velocity and the read-only debug getters. No per-tick cross-system notifications are specified.
- Exact replacement, cancellation, arrival and failure notification semantics are **UNDECIDED** beyond the current behavior below. API signatures, state names, notification contracts, queues and hidden states are not prescribed.
- Movement does not call visual, input, UI or future gameplay systems. Other gameplay systems enter the dependency map only through later approved tickets.

## Earlier confirmed movement behavior

These owner decisions predate Movement v3. Task #28 superseded the near-opposite rule (no reversal threshold); the reversal task on `orientation` restored it (**Reversal rule** below). Task #28 implements turning from rest only through speed (no turning at exactly zero speed); arrival ends commanded rotation. Task #46 applies the route-vertex rule below to its navigation routes. Whether each still applies is for the Movement v3 tickets (Tasks 15–17) and later ones to state:

- From rest, translation and turning begin together. Movement accommodates forward, backward, lateral and diagonal directions. Short journeys may end before the hull faces the destination.
- While moving, turns are relatively wide and momentum-aware; the ship follows a continuous trajectory.
- A near-opposite order (150°, relative to actual travel) brakes to rest before stationary movement begins.
- Arrival ends commanded rotation; there is no final alignment phase.
- Intermediate route vertices are not arrival targets; route following avoids stop/start, heading resets and jitter.

## Movement v3 (Tasks #27, #28, #29, #30, #41, #44 and #46)

**Reaction delay (Task #30):** `move_to()` and `stop()` only *receive* a command. Each is appended to one per-ship FIFO queue with `due = received + reaction_delay` on Movement's physics clock (the sum of physics `delta`; input between ticks is stamped with the last tick's clock). At the start of each physics tick, before step 1, the clock advances and every command with `due ≤ clock` is activated in receipt order. A move then sets the destination, the order flag and the course heading from the ship's position **at activation**, and classifies it once for the reversal rule (below). A stop clears the order, so ordinary thrust-limited braking follows. Until then the active order (or idle braking) stands unchanged. A later command never cancels, merges with or reorders an earlier pending one, and stop has no bypass (owner: "Yes", issue #30). Commands due on the same tick are all applied in order, so the last one decides that tick. A delay of 0 activates on the next tick. Activation is quantized to the tick: with 60 Hz and float summation it lands 0 or 1 tick (≤ 16.7 ms) after the due time. Each receipt and activation is logged with `print()`.

Movement uses `CharacterBody3D` in floating mode with one `move_and_slide()` per physics tick and built-in physics interpolation. There is one world-space planar velocity (the built-in `velocity`, Y = 0) and one heading. No velocity channels are combined, no existing velocity is rotated, and there is no mode or phase state. The only rotational state is one per-ship turn rate and the current order's course heading; one more float, last tick's planar demand fraction, is kept for yaw-braking planning.

Each physics tick (everything read at the start of the tick, including the bow; turning demand is computed before the desired velocity, but the list keeps the propulsion order):

1. **Arrival:** an active order completes when the ship is within `arrival_tolerance` of its destination **and** its planar speed is at most `arrival_speed_tolerance`. Being inside the tolerance at higher speed is not arrival.
2. **Desired velocity** (arrival steering, Reynolds): with an active order, toward the destination at `clamp(sqrt(2 · a_plan · d) − a_plan · pilot_response_time, 0, max_speed)`. **Response-lag compensation (Task #41):** step 3 closes the gap through `pilot_response_time`, so the plain braking curve would leave the ship `a_plan · pilot_response_time` (3 m/s at 12 m/s²) too fast at the start of braking, crossing the destination and reversing; subtracting that lag makes the request exactly `−a_plan` while the ship is on the curve `sqrt(2 · a_plan · d)`. The desired speed is 0 within `a_plan · pilot_response_time² / 2` (0.375 m at 12 m/s²) of the destination, inside the arrival tolerance. No tuning value is added. Here `d` is the planar distance, `a_t = thruster_strength / mass` (the thrusters are the only brake) and **`a_plan = a_t / (1 + f_r)`**: the braking that proportional sharing leaves a saturated planar demand beside this tick's turning demand `f_r` (step 6), so 12 m/s² with no turn and 6 m/s² at full turn (owner-approved trial, PR #32). **Retro rule in planning (Task #29):** with `s = w · bow`, where `w` is the direction of the actual planar velocity (the direction to the destination only at exactly zero speed), `a_plan = min(a_t / (1 + f_r), L / s)` when `s > 0`; `L` is the sternward limit of step 7. With retro thrusters `L` is unlimited, so this is unchanged. Forward travel without retro plans at 5.4 m/s², sideways at 12, stern-first at 12. Without an order (after arrival or `stop()`) it is zero. It is never assigned to `velocity`. **Route guidance (Task #46):** a routed order replaces "toward the destination at distance `d`" with the guidance direction and the remaining path length, and caps the speed for each route corner ahead: `sqrt(a_b · R + 2 · a_b · d_corner) − a_b · pilot_response_time` with `a_b = min(a_plan, a_t / 2)` (the planar share proportional sharing leaves beside full turning demand) and the corner's guidance radius `R`. The direct order is unchanged. **Momentum-preserving course changes (owner tasks on `orientation`):** while the ship moves bow-first (`velocity · bow > 0`) with an order, let `w` be the actual travel direction, `u` the steering direction, `θ` the angle between them and `v_d` the desired speed from the laws above. `a_r` is the acceleration the main engine (up to `main_acceleration` along the bow) and the thrusters' whole envelope can deliver across `w` toward `u` (`ShipPilot.redirect_acceleration_of`, by bisection), and the step is `asin(a_r · pilot_response_time / v)` (no limit when the argument reaches 1; the sweep then never applies, also at exactly 180°, where single-precision `angle_to()` exceeds the double-precision π). When `θ` exceeds the step, `v_d ≥ v` (the arrival and bend laws do not ask to slow) and the full-direction request `(u · v_d − velocity) / pilot_response_time` has a braking part in the allocator's per-hull-axis split, that request brakes only because the direction differs; the desired velocity is then `w` turned toward `u` by the step (so the lateral request equals `a_r`) at the actual speed `v` (a speed-up waits for the new direction), and that speed is further limited so the turn can still stop at the steering point: on the holdable circle of radius `v² / a_s` (`a_s` the same reach within the share `1 / (1 + f_r)`), the straight leg left to the point, `sqrt(d² − 2 r d sin θ')`, must hold the stopping distance `v² / (2 a_plan)` (`θ' = min(θ, 90°)`, so a point abeam or behind uses the abeam circle), i.e. the largest `u = v²` with `u² / (4 a_plan²) + u · 2 d sin θ' / a_s ≤ d²`. Otherwise the desired velocity is `u · v_d` as before. **Course following (direct orders):** the order's course is `w` turned toward `u` by at most the step (the bearing itself within the step, at rest, at low speed and stern-first), recomputed every tick, until the first tick the arrival law (`sqrt(2 · a_plan · d) − a_plan · pilot_response_time`, before the speed cap) is below the actual speed; from then on it holds for the rest of the order (`ShipPilot.Targets.course_follows`, kept by the caller). It replaces PR #32's course fixed at activation; the hold keeps PR #32's protection against the late arrival spin. The course set on a tick steers from the next one (turning demand is computed first). The reference is the actual velocity every tick, so nothing accumulates; no velocity is rotated and no force is added; there is no mode, and the only new per-order state is the hold flag. The allocator, its braking-first priority and every limit are unchanged.
3. **Requested acceleration:** `(desired − velocity) / pilot_response_time`.
4. **Main engine:** along the current bow only, `clamp(requested · bow, 0, main_acceleration)`. It is 0 whenever `velocity · bow < 0`, so it never reduces the current speed (non-negative work).
5. **Planar demand:** `t_req = requested − bow · main`, as a fraction `f_t = min(N(t_req), 1)` of the speed-dependent thruster envelope `N` (see **Speed-dependent directional thrust** below; at rest `N = |t| / a_t`, as before).
6. **Turning demand:** available authority `α_max = turn_acceleration_curve(v)` (°/s²) and turn-rate limit `ω_max = turn_rate_curve(v)` (°/s), two independent curves of the **actual** start-of-tick speed `v` in m/s (frigate: 0.5 / 10 / 7 / 3.5 °/s² and 1.8 / 35 / 30 / 20 °/s at 0 / 5 / 10 / 15 m/s, linear between: weak in place, a low-speed peak, falling toward cruise). The target is the order's **course heading**: for a direct order set when a move command activates, from the ship toward the destination (none for a zero-length order), then following the travel direction and the bearing until arrival braking begins and held from then on (step 2); positional correction after an overshoot never changes it, and a new order replaces it. Route guidance sets its own course every tick (its aim, then the frozen final approach). **Bow alignment:** while the velocity has a bow-first component (`velocity · bow > 0`), the steering target is that course limited to `bow_alignment_curve(speed)` either side of the actual travel direction, `target = ψ_v + clamp(wrap(ψ_c − ψ_v), −θ_max, θ_max)`, recalculated every tick from the actual velocity, so the hull leads a turn by at most `θ_max` and the target reaches the course as the trajectory follows; at rest, stern-first or sideways (`velocity · bow ≤ 0`) the target is the course itself. It limits the target only: the hull and the velocity are never moved into line, and the angle can briefly exceed `θ_max` while the hull responds. It applies to every course the pilot is given (the direct order's, route guidance's aim and the final-approach freeze); departures command no course and are unaffected. With an active order, a course and `α_max > 0`, with the shortest error `e`, the wanted rate is `sign(e) · min(sqrt(2 · α_plan · |e|), |e| / delta, ω_plan)` with **`α_plan = α_low / (1 + f_t_prev)`**, where `α_low` and `ω_plan` are the lowest values of the two curves between `v` and the speed left after the time the turn needs to stop (`|rate| (1 + f_t_prev) / α`, iterated twice) at last tick's deceleration (`(v_prev − v) / delta`, 0 when not slowing; one more float of per-ship state). Slowing toward rest lowers both curves, so the turn is planned with what will be left and the rate stays within the limit it will meet. the turn's share if planar demand stays at last tick's fraction `f_t_prev` (owner-approved trial, PR #32; `f_t_prev` starts at 0 and carries over order replacement and `stop()`, since it measures actual thruster demand) (braking-distance rule; the `|e| / delta` term is only a numerical aid, and the heading can still cross the target). The request `α_req = (wanted − rate) / delta` gives `f_r = min(|α_req| / α_max, 1)`. Otherwise `f_r = 0` and the turn rate is set to 0: rotation does not persist without powered turning (intentional non-Newtonian rule).
7. **Shared capacity:** if `f_t + f_r > 1`, both are scaled by `1 / (f_t + f_r)` (owner-approved proportional sharing). The planar share `f_t / max(1, f_t + f_r)` is filled **braking first, sideways maneuvering second, forward assistance last** (below). At full demand on both, the thrusters give 6 m/s² and turning half its rated authority. The main engine is outside this capacity. **Retro rule (Task #29):** when `retro_thrusters` is false, the thruster command's component toward the stern (along −bow) may not exceed `L = no_retro_braking_effectiveness × a_t` (5.4 m/s²). After sharing, only the excess sternward part is removed: lateral and bow-forward parts are untouched, nothing is scaled up and the removed capacity is not reallocated (to turning either). The turning and planar fractions are computed before the cap. It applies to all sternward thrust: braking a bow-first motion and accelerating stern-first (owner-provisional, "Yes I agree until I see it").
8. **Integration:** `rate = clamp(rate + α · delta, −ω_max, ω_max)` (when the limit contracts faster than the authority can slow the turn, the rate is clamped, never the heading); `velocity += (bow · main + thrusters) · delta`, planar magnitude hard-clamped to `max_speed`; `yaw += rate · delta`; then `move_and_slide()`.

**Reversal rule (owner task on `orientation`, restores the original near-opposite rule):** when a move activates (after the reaction delay), `ShipPilot.reversal_angle_of()` measures the angle between the **actual planar velocity** (not the bow) and the direction from the ship to the click; it is not measured at or below `arrival_speed_tolerance` (stationary: existing movement) or within `arrival_tolerance` (an arrival). At or beyond `near_opposite_angle` (150°, inclusive) the order commits to braking first (`ShipPilot.Targets.brake_first`, kept by the caller like the course state). While committed and the order is active, step 2 requests zero velocity and step 6 commands no turn (`f_r = 0`, the turn rate is 0, as for departures), so the thrusters brake along the travel direction with the whole capacity and nothing destination-directed cancels the stop; the destination stays active. The first tick the actual speed is at or below `arrival_speed_tolerance`, `step()` clears the commitment and that tick already follows the ordinary rules (an order from near rest: translation and turning together, the main engine as the hull aligns). The decision is never re-evaluated; a new move classifies afresh and a stop clears it. No timer, threshold speed, drag or snap is added; the braking is the ordinary thrust-limited braking.

**Speed-dependent directional thrust (owner-approved tasks, provisional values):** the directional thrusters have three independent limits in the bow frame, each at the **actual** planar speed `v` at the start of the tick in m/s, with `e = directional_thrust_curve(v)` clamped to 0–1 (the curve's domain is m/s; speeds past its end points use those points' values):
- **Sideways (repositioning):** `a_r = a_t × e`. Frigate 3.33 / 2.50 / 1.67 / 0.83 m/s² at 0 / 5 / 10 / 15 m/s.
- **Bow-forward:** physically `a_r` like sideways, but **forward assistance** (bow-forward thrust that pushes the ship forward rather than braking stern-first motion) is limited to `a_f = forward_directional_acceleration × e` (not divided by mass). The main engine is the primary forward propulsion; the directional thrusters only assist. Frigate `a_f` 0.25 / 0.1875 / 0.125 / 0.0625 m/s² at 0 / 5 / 10 / 15 m/s, against the engine's 0.5. Bow-forward braking of stern-first motion keeps `a_r`.
- **Sternward:** the full `a_t` (then the retro rule, unchanged).

The physical envelope norm of a thrust `t` with axial part `x = t · bow` and lateral part `y` is `N(t) = sqrt((x / A)² + (y / a_r)²)` with `A = a_r` when `x > 0` and `A = a_t` otherwise: a half-circle toward the bow joined to a half-ellipse toward the stern, convex, no direction above `a_t`, nothing adds capacity. Forward assistance must also stay within `share × a_f`. The planar demand `f_t` is `min(1, max(N(t_req), |forward assistance| / a_f))`.
- **Split (step 7):** `t_req` is split per hull axis into three parts that sum to it. **Braking:** on each axis (along the bow, sideways), the thrust opposing the velocity on that axis, up to `|v_axis| / pilot_response_time` (the rate the pilot requests to remove that velocity; more pushes the other way and is not braking). **Forward assistance:** the remaining bow-forward thrust. **Maneuvering:** everything else (sideways thrust that does not brake, and sternward thrust that does not brake).
- **Priority (step 7):** if the whole request fits (`N ≤ share` and forward assistance `≤ share × a_f`), it is applied as is. Otherwise braking, then maneuvering, then forward assistance each get the largest scale in 0–1 that keeps `N` of everything allocated so far within the share (exact for the first non-zero part, bisection afterwards; `N` is convex), forward assistance also capped at `share × a_f`. A later part never reduces an earlier one and never uses capacity an earlier one could use. Nothing is scaled up; turning keeps its proportional share.
- **Braking planning (step 2):** `a_plan = reach(−w) / (1 + f_r)`, then the retro rule as before, where `reach(d) = 1 / N(d)` is the envelope's acceleration along the unit direction `d` at the actual speed and `w` the actual travel direction (the steering direction at rest). Bow-first braking keeps `a_t` (3.33 m/s²); sideways drift brakes at `a_r`; stern-first travel brakes with bow-forward thrust at `a_r` (the main engine never brakes; the forward-assistance limit does not apply to braking). The plan uses the current speed's `e`; with a curve that does not rise with speed, braking only gets stronger as the ship slows.
- **Route bends (step 2):** a corner's hold term `a_b · R` is limited to `v_h²`, where `v_h² = (a_t / 2) · e(v_h) · R` (half the sideways limit at the hold speed itself; bisection over 0–`max_speed`).
- No mode, threshold or alignment; the main engine, turning sharing and the velocity integration are unchanged. Task #60 retired the drift-corridor and skipped-flight estimates. Its stopping-room checks use the directional envelope and actual physical state; the existing destination resolver is retained.

Yaw never rotates the velocity. The speed-linked rate limit is the only yaw-rate cap (owner-approved trial, PR #32); there is no heading snap or final alignment. There is no position hold, snap or speed reset: after arrival or `stop()` the ship brakes toward zero velocity wherever it is. A small overshoot at low speed can still occur (the destination is passed below the arrival speed and the ship rests just past it); a genuine miss is corrected normally.

**Static contact (Task #44):** right after `move_and_slide()`, each slide collision is checked. It qualifies when the collider is a `StaticBody3D` but not an `AnimatableBody3D`, and this tick's attempted planar velocity (before the slide) has a negative dot product with the collision normal's XZ projection (driving into the surface; glancing contact included). On the first qualifying collision the active order ends (the pending queue is untouched, `stop()` is not used), `velocity` and the turn rate become 0, the position stays where the engine left it, and one line is logged. It applies with or without an active order (coasting or braking). Resting or outward contact never qualifies, so an order away from a touching obstacle proceeds. No state, getter, signal or tuning value was added. Contact with any other body type keeps Godot's default sliding; no hard-stop rule is promised for it.

## Navigation (Tasks #46, #48, #54 and #60)

Task #60 uses **Navigator → lookahead and physical clearance → the existing ShipPilot**. A pending route job never removes the pilot target. There is no activation coast, additional reaction delay, full-flight candidate approval, stopping simulation or certificate chain. The pilot's physics and tuning are unchanged.

- **Route acquisition:** one ordinary Godot path from the actual ship position, with Task #54's existing blocked-click resolver, bounded candidate search and query counts. A path is guidance, not a required trajectory. An activated new command cancels old work and guidance immediately, preserving physical momentum and the FIFO due times. The order's reversal commitment is still classified once at activation.
- **Following:** `RouteGuidance` retains lookahead, position-based corner progress, bend limits and frozen final approach. While a job is pending, the active order can already respond toward its requested destination under the same physical clearance check. Once resolved, guidance and the F3 marker use the resolved destination. Navigation unavailable or clicks outside the region bounds retain the earlier direct/contact-fallback behavior.
- **Clear space:** `HullProbe.open_stopping_room()` derives a conservative response-and-stop envelope from current position, velocity, available acceleration, the minimum directional effectiveness and the no-retro cap. The stopping-distance bound includes `v² / (2 a_min)`, the proportional-response remainder and an integration tick. With retro thrusters, no-order braking is parallel to velocity, allowing a capsule; without them a containing ball is used. A swept all-yaw cylinder covers the actual hull throughout the capsule. No braking ticks or future journeys are simulated.
- **Centre no-go rule:** the same baked mesh and `no_go_tolerance` remain authoritative. A read-only cache of the existing mesh boundary edges proves an entire disk/capsule lies on the mesh, including any enclosed hole. Internal polygon edges cancel; region seams may conservatively reject a proof. It has no adjacency graph, authored geometry or route-search role. The cache is shared by ships in the same map, built incrementally and invalidated by map iteration. A failed quick check means local examination, not unreachable.
- **Near constraints:** `ManeuverRollout.local_clear()` copies the actual state and targets, calls the same `ShipPilot.step()` for the immediate response, checks the rotating hull sweep, then tests physical stopping room geometrically. There is no persistent predicted state or async trajectory handoff. A line crossing a no-go edge is never treated as clear merely because float closest points differ slightly. Where exact mesh containment fails, closest-point samples reserve a half-interval Lipschitz margin, covering intermediate positions within the existing tolerance. A ship spawned inside a zone retains the earlier exemption only until it first reaches the mesh; that history is never reset on a later command or local check.
- **Physical slowing/repositioning:** insufficient maneuvering room requests ordinary zero-target braking. Near rest, the existing held-heading translation capability can reposition away from the nearest baked boundary, using `departure_step_time` (0.5 s requests), `departure_max_time` (4 s total commanded repositioning) and the existing lookahead distance. Each response is checked against the real hull and centre rule. A temporary reposition does not overwrite the direct order's course state. If no local move is possible at rest, or the bounded repositioning is exhausted, the destination remains **blocked (unresolved)** until a new command; the same failed search is not repeated indefinitely. Static contact remains the physical fallback. There is no different-passage search; that is Issue #61.
- **Shared work:** `Navigator` accounts for preparation, path/resolver work, cancellation/handoff and live guidance/clearance against the existing 1,500 μs/tick allowance. `PlanClock` slices path and boundary-cache work, reserving measured live-guidance cost; background boundary preparation gets at most half the available slice. This does not hold movement. Atomic engine queries and local geometric checks are measured rather than claimed to have a hard real-time guarantee; any observed overrun must be reported.
- **Retired:** `ManeuverPlanner`, `CorridorScan`, full-flight rollout regions/skips/departure search, braking-wait validation and the experimental segment-certificate mode. `plan_prediction_per_order` remains serialized for compatibility but is unused by this implementation. No new tuning value, top-level module or dependency was added.

## Reusable ship composition

The reusable ship scene `Ships/ship.tscn` separates authoritative movement from a visual/model child `Visual` (a plain `Node3D` wrapper). Only that child may ever tilt visually; the authoritative root and collision never tilt.

Banking is **deferred**: Task #27 deleted the former `ShipVisualBank` script and `ShipBankProfile` resource, since they read Movement's removed API (Git history, `main` at a174d22).

Shared function and appearance use one authoritative scene/script/resource. Ship differences use configuration rather than duplicated implementations; check existing assets before creating another shared definition. Per-instance runtime state must not modify shared resources.

## Data and validation

Per-ship tuning belongs in Godot `Resource` data assets, not code constants. Shared assets hold configuration only; runtime state belongs to the individual ship. Each tunable requires a default, unit and owner-approved range. `MovementProfile` holds the provisional values (see the inventory). Start conservatively and adjust in play.

The first playable work uses one ship in open space in the developing game scene, rather than multiple test scenes. The intended battle scale is tens of units; assess it with real combat later, without treating that intention as a measured performance target.

The rejected upfront alternative is a global command/orchestration framework, an independently deployable navigation system and custom simulation. They add coupling and complexity before confirmed users require them.
