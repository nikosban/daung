# Architecture

## Status and units

This is the target design approved in Task #1. Task #27 (Movement v3, Task 1 of 4) replaced the earlier Movement implementation with a rewrite, Task #28 (Task 2 of 4) added speed-dependent powered turning, Task #29 (Task 3 of 4) added the retro-thruster capability, and Task #30 (Task 4 of 4) added the crew reaction delay; Task #41 compensated the arrival braking for the pilot response lag; Task #44 added the static-contact stop; Task #46 added hull-aware static navigation (one planning job per order, route guidance); Task #50 closed three false-safe paths in its prediction (corridor shortcut off the route, handoff from an unvalidated state, direct course); Task #48 widened the baked clearance into an ordinary-transit no-go zone (13.75 m agent radius), declines clicks inside it and rejects predicted maneuvers whose centre would enter it; the actual inventory is listed below.

**1 world unit = 1 metre.** Gameplay movement is horizontal on Godot's X/Z plane. Ordinary movement does not chase Y; any later vertical animation belongs to the model only.

Data assets use m/s for speed, m/s² for acceleration, s for times, and metres for dimensions and distances. **Thrust units** are m/s² × the dimensionless gameplay mass divisor, so thrust / mass gives m/s². Angles are in degrees in data and debug output (radians internally). **Turn-authority units** are °/s² × the mass divisor, so turn_authority / mass gives °/s².

## Module map

| Module | Owns | May use | Status |
|---|---|---|---|
| Movement | Move/stop requests; authoritative open-space position, one world planar velocity and yaw; pilot guidance and propulsion (internal); static navigation planning and route guidance (internal, Task #46); movement-profile definitions | Godot engine APIs only | Implemented (Movement v3 slices 1–2: arrival-steering pilot, main engine, directional thrusters, speed-dependent powered turning sharing the thruster capacity; slice 3: retro-thruster capability; slice 4: reaction-delay command queue; Task #44: static-contact stop; Task #46: hull-aware navigation around static obstacles) |

Movement is the only top-level gameplay module. Pilot guidance, propulsion and navigation are internal responsibilities, not independently exposed global modules. Task #46 returned path queries and route corners to Movement (Godot's `NavigationServer3D` and physics shape queries, both engine APIs); destination resolution is a later ordered ticket. Main owns the static navigation geometry (`NavigationRegion3D`). Scene-level mouse/camera input is composition glue, not a module.

Dependencies follow the one-way May-use map. Changes require an approved ticket stating the map change. Enforcement is review-only; no dependency tooling is installed or planned here.

## Movement boundary and authority

The command flow is caller → move-to or stop request → Movement's pilot → propulsion → authoritative ship transform.

- Movement alone writes the ship's authoritative transform and owns its heading and velocity. External callers request movement rather than writing transforms.
- Callers may read velocity and the read-only debug getters. No per-tick cross-system notifications are specified.
- Exact replacement, cancellation, arrival and failure notification semantics are **UNDECIDED** beyond the current behavior below. API signatures, state names, notification contracts, queues and hidden states are not prescribed.
- Movement does not call visual, input, UI or future gameplay systems. Other gameplay systems enter the dependency map only through later approved tickets.

## Earlier confirmed movement behavior

These owner decisions predate Movement v3. Task #28 superseded the near-opposite rule (no reversal threshold) and implements turning from rest only through speed (no turning at exactly zero speed); arrival ends commanded rotation. Task #46 applies the route-vertex rule below to its navigation routes. Whether each still applies is for the Movement v3 tickets (Tasks 15–17) and later ones to state:

- From rest, translation and turning begin together. Movement accommodates forward, backward, lateral and diagonal directions. Short journeys may end before the hull faces the destination.
- While moving, turns are relatively wide and momentum-aware; the ship follows a continuous trajectory.
- A near-opposite order (150°, relative to actual travel) brakes to rest before stationary movement begins.
- Arrival ends commanded rotation; there is no final alignment phase.
- Intermediate route vertices are not arrival targets; route following avoids stop/start, heading resets and jitter.

## Movement v3 (Tasks #27, #28, #29, #30, #41, #44 and #46)

**Reaction delay (Task #30):** `move_to()` and `stop()` only *receive* a command. Each is appended to one per-ship FIFO queue with `due = received + reaction_delay` on Movement's physics clock (the sum of physics `delta`; input between ticks is stamped with the last tick's clock). At the start of each physics tick, before step 1, the clock advances and every command with `due ≤ clock` is activated in receipt order. A move then sets the destination, the order flag and the course heading from the ship's position **at activation**. A stop clears the order, so ordinary thrust-limited braking follows. Until then the active order (or idle braking) stands unchanged. A later command never cancels, merges with or reorders an earlier pending one, and stop has no bypass (owner: "Yes", issue #30). Commands due on the same tick are all applied in order, so the last one decides that tick. A delay of 0 activates on the next tick. Activation is quantized to the tick: with 60 Hz and float summation it lands 0 or 1 tick (≤ 16.7 ms) after the due time. Each receipt and activation is logged with `print()`.

Movement uses `CharacterBody3D` in floating mode with one `move_and_slide()` per physics tick and built-in physics interpolation. There is one world-space planar velocity (the built-in `velocity`, Y = 0) and one heading. No velocity channels are combined, no existing velocity is rotated, and there is no mode or phase state. The only rotational state is one per-ship turn rate and the current order's course heading; one more float, last tick's planar demand fraction, is kept for yaw-braking planning.

Each physics tick (everything read at the start of the tick, including the bow; turning demand is computed before the desired velocity, but the list keeps the propulsion order):

1. **Arrival:** an active order completes when the ship is within `arrival_tolerance` of its destination **and** its planar speed is at most `arrival_speed_tolerance`. Being inside the tolerance at higher speed is not arrival.
2. **Desired velocity** (arrival steering, Reynolds): with an active order, toward the destination at `clamp(sqrt(2 · a_plan · d) − a_plan · pilot_response_time, 0, max_speed)`. **Response-lag compensation (Task #41):** step 3 closes the gap through `pilot_response_time`, so the plain braking curve would leave the ship `a_plan · pilot_response_time` (3 m/s at 12 m/s²) too fast at the start of braking, crossing the destination and reversing; subtracting that lag makes the request exactly `−a_plan` while the ship is on the curve `sqrt(2 · a_plan · d)`. The desired speed is 0 within `a_plan · pilot_response_time² / 2` (0.375 m at 12 m/s²) of the destination, inside the arrival tolerance. No tuning value is added. Here `d` is the planar distance, `a_t = thruster_strength / mass` (the thrusters are the only brake) and **`a_plan = a_t / (1 + f_r)`**: the braking that proportional sharing leaves a saturated planar demand beside this tick's turning demand `f_r` (step 6), so 12 m/s² with no turn and 6 m/s² at full turn (owner-approved trial, PR #32). **Retro rule in planning (Task #29):** with `s = w · bow`, where `w` is the direction of the actual planar velocity (the direction to the destination only at exactly zero speed), `a_plan = min(a_t / (1 + f_r), L / s)` when `s > 0`; `L` is the sternward limit of step 7. With retro thrusters `L` is unlimited, so this is unchanged. Forward travel without retro plans at 5.4 m/s², sideways at 12, stern-first at 12. Without an order (after arrival or `stop()`) it is zero. It is never assigned to `velocity`. **Route guidance (Task #46):** a routed order replaces "toward the destination at distance `d`" with the guidance direction and the remaining path length, and caps the speed for each route corner ahead: `sqrt(a_b · R + 2 · a_b · d_corner) − a_b · pilot_response_time` with `a_b = min(a_plan, a_t / 2)` (the planar share proportional sharing leaves beside full turning demand) and the corner's guidance radius `R`. The direct order is unchanged.
3. **Requested acceleration:** `(desired − velocity) / pilot_response_time`.
4. **Main engine:** along the current bow only, `clamp(requested · bow, 0, main_acceleration)`. It is 0 whenever `velocity · bow < 0`, so it never reduces the current speed (non-negative work).
5. **Planar demand:** `t_req = requested − bow · main`, as a fraction `f_t = min(|t_req| / a_t, 1)`.
6. **Turning demand:** rated authority `α_max = (turn_authority / mass) × rudder_curve(speed / max_speed)` and turn-rate limit `ω_max = max_turn_rate_at_max_speed × rudder_curve(speed / max_speed) / rudder_curve(1)`, both from the **actual** start-of-tick speed (both 0 at rest only when the curve is 0 at speed 0; the owner's frigate curve is 0.05 there, so it turns slowly in place). The target is the order's **course heading**, set once when a move command activates, from the ship toward the destination (none for a zero-length order); positional correction after an overshoot never changes it, and a new order replaces it. With an active order, a course and `α_max > 0`, with the shortest error `e`, the wanted rate is `sign(e) · min(sqrt(2 · α_plan · |e|), |e| / delta, ω_max)` with **`α_plan = α_max / (1 + f_t_prev)`**, the turn's share if planar demand stays at last tick's fraction `f_t_prev` (owner-approved trial, PR #32; `f_t_prev` starts at 0 and carries over order replacement and `stop()`, since it measures actual thruster demand) (braking-distance rule; the `|e| / delta` term is only a numerical aid, and the heading can still cross the target). The request `α_req = (wanted − rate) / delta` gives `f_r = min(|α_req| / α_max, 1)`. Otherwise `f_r = 0` and the turn rate is set to 0: rotation does not persist without powered turning (intentional non-Newtonian rule).
7. **Shared capacity:** if `f_t + f_r > 1`, both are scaled by `1 / (f_t + f_r)` (owner-approved proportional sharing). At full demand on both, the thrusters give 6 m/s² and turning half its rated authority. The main engine is outside this capacity. **Retro rule (Task #29):** when `retro_thrusters` is false, the thruster command's component toward the stern (along −bow) may not exceed `L = no_retro_braking_effectiveness × a_t` (5.4 m/s²). After sharing, only the excess sternward part is removed: lateral and bow-forward parts are untouched, nothing is scaled up and the removed capacity is not reallocated (to turning either). The turning and planar fractions are computed before the cap. It applies to all sternward thrust: braking a bow-first motion and accelerating stern-first (owner-provisional, "Yes I agree until I see it").
8. **Integration:** `rate = clamp(rate + α · delta, −ω_max, ω_max)` (when the limit contracts faster than the authority can slow the turn, the rate is clamped, never the heading); `velocity += (bow · main + thrusters) · delta`, planar magnitude hard-clamped to `max_speed`; `yaw += rate · delta`; then `move_and_slide()`.

Yaw never rotates the velocity. The speed-linked rate limit is the only yaw-rate cap (owner-approved trial, PR #32); there is no heading snap or final alignment. There is no position hold, snap or speed reset: after arrival or `stop()` the ship brakes toward zero velocity wherever it is. A small overshoot at low speed can still occur (the destination is passed below the arrival speed and the ship rests just past it); a genuine miss is corrected normally.

**Static contact (Task #44):** right after `move_and_slide()`, each slide collision is checked. It qualifies when the collider is a `StaticBody3D` but not an `AnimatableBody3D`, and this tick's attempted planar velocity (before the slide) has a negative dot product with the collision normal's XZ projection (driving into the surface; glancing contact included). On the first qualifying collision the active order ends (the pending queue is untouched, `stop()` is not used), `velocity` and the turn rate become 0, the position stays where the engine left it, and one line is logged. It applies with or without an active order (coasting or braking). Resting or outward contact never qualifies, so an order away from a touching obstacle proceeds. No state, getter, signal or tuning value was added. Contact with any other body type keeps Godot's default sliding; no hard-stop rule is promised for it.

## Navigation (Tasks #46, #48 and #50)

**No-go zone (Task #48, owner Option A):** the baked mesh's exclusion around an obstacle (agent radius 13.75 m, so 19.75 m from the 6 m sphere's centre on its axes) is the static no-go zone for ordinary transit, defined for the ship's **centre**: routes run outside it, clicks inside it are declined, and a predicted maneuver whose centre would go more than `no_go_tolerance` beyond the mesh edge is rejected. The rotating hull may extend into the zone; only the physical obstacle may never be touched. It is a planning rule, not a physical boundary: no wall, snap or steering force. Unpredicted routes (no hazard regions, from rest) are not checked; the pilot's lookahead can cut the hole's polygon corners by up to about 0.5 m (measured).

Each activated move starts **one planning job** (`Navigator`); nothing is re-planned without a new order. Until the job finishes, the ship has no guidance and brakes exactly as it does without an order (`has_order()` stays true; `is_planning()` reports the wait). A later move or stop activating cancels the job; its result is never applied. The FIFO due times are unchanged.

- **Scheduling:** jobs of all ships share one wall-clock allowance per physics tick (`NavigationBudget.plan_time_per_tick`), served oldest first; a job only waiting for navigation to sync does not hold up the others. All planning work, preparation included, runs in small items (one readiness check, one classification, one path query with route cleanup, one route sample, one corridor sample, one predicted tick whose hull check covers at most 16 ticks); a `PlanClock` starts an item only if it can end before the deadline at the longest item duration measured so far (held back at most half the allowance), so a slice stays within its allowance. An unfinished job continues on the next tick (the same job). The per-tick allowance only spreads work over ticks; it never changes an outcome. The per-order limit counts **predicted flight time** over all of an order's candidate predictions (`NavigationBudget.plan_prediction_per_order`), so the same order from the same ship state always gets the same result on any machine (PR #47 review: the former wall-clock per-order limit made identical clicks succeed or fail at random). A ship that moves while its job waits gets a validation with a predicted braking wait and a handoff on a fixed frame (see Validation), which can still make a moving ship's outcome depend on how many ticks the job took. A single unobstructed order finishes in its activation tick, so its flight is bit-identical to the pre-Task #46 direct order.
- **Readiness:** map inactive or iteration 0, or an enabled region with region iteration 0: wait (no path query). No enabled region once the map has synced: navigation unavailable. Regions synced but no polygon merged (no closest-point owner): wait while the map iteration still changes; after `MERGE_WAIT_FRAMES` (2) frames without change, unavailable.
- **Classification:** navigation unavailable, or a click outside every enabled region's XZ bounds (the region bounds equal the mesh AABB, verified), keep the **direct order (baseline)**, logged. A click inside the bounds but more than one map cell (0.25 m) from the mesh lies in a no-go zone and is **declined** ("destination inside a no-go zone", Task #48; no substitute destination until destination resolution). An empty path declines the order, and so does a path whose end does not reach the click along a straight leg that stays on the mesh (sampled every cell). Godot can end a path short of an on-mesh target (observed: (97.43, −12.02) for a click on (98, −12), 0.57 m away); the route then ends with that leg. Otherwise the route is the ship, the path corners and the click (Y at the ship; a path start within one cell of the ship is the ship; corners within one cell of the line between their neighbours are dropped).
- **Hazard regions:** route samples every hull half-width where a cylinder of radius hull reach + `plan_clearance_buffer` around the root is not empty (the hull might touch something there at some yaw), each with a lead-in of one stopping distance at max speed (`max_speed² / (2 · a_t)`, 33.8 m for the frigate); closer regions merge. The start and end samples are included (departure, final approach).
- **Drift corridor:** a ship moving at `v` can drift sideways off the route by at most `v² / a_t` (its braking distance at the planar share left beside full turning, `a_t / 2`). The corridor is clear when the ship's position and every route sample ahead have an empty cylinder of radius hull reach + buffer + `v² / a_t`.
- **No prediction** when there are no hazard regions and the ship is at rest or its drift corridor is clear. Otherwise candidates are **predicted** from the ship's actual state with the real pilot (`ShipPilot.step`) and the real hull (`HullProbe`), in order: the direct order (2-point route) or route guidance; then departures in each direction (braking for a moving ship, then astern, port, starboard, ahead). A clearance-mode prediction first finds when a departure in that direction gives the hull room to turn (a cylinder of hull reach + `plan_clearance_buffer` around the root empty, at most `departure_max_time`) or when it runs into something; a direction with room is tried at once with the departure that switches to the route exactly then. Then fixed departures of one to several `departure_step_time` steps up to `departure_max_time` (0.5 s … 4 s, shorter first): in a direction with room only those longer than its time to room (the slow-turning frigate often needs more distance to line up with the route), in a direction that runs into something only those that end before the contact. Each departure then follows the route. A departure commands no course, so rotation stops at once (no powered turning) and the hull keeps its heading with the whole thruster capacity for braking or translating. The first candidate whose prediction passes is handed to the pilot. A first candidate that fails after its prediction had settled onto the route ends the search. No candidate passes: decline.
- **Prediction:** tick by tick through every hazard region and every open stretch until the predicted ship has settled onto the route (past the last region it passes as soon as its drift corridor is clear, checked every 0.5 s of predicted flight, 8 corridor samples per predicted tick; **Task #50:** only while the predicted centre is within `arrival_tolerance` of the route, with the corridor radius grown by that off-route distance: the corridor bounds drift off the route, not a ship's way back to it, which is predicted tick by tick) (within `arrival_tolerance` of it, hull and velocity within 2° of its direction, turn below 0.5°/s). Only after settling may an open stretch of at least one stopping distance be skipped: the next region then starts from the re-entry assumption (on the route, hull along it, the speed the speed law allows there, no turn), which is not proof. The final region runs to rest (below 0.01 m/s, at most 20 s); the resting pose must be clear. All durations are in seconds and advance by the physics `delta`, so maneuvers keep their timing at any physics tick rate.
- **No-go check (Task #48):** each predicted tick (not the braking wait, not clearance mode) queries the map's closest point to the predicted centre. Once the centre has been within one map cell of the mesh, a tick more than `no_go_tolerance` beyond it fails the candidate ("centre enters the no-go zone at (x, z)"); a ship starting inside a zone may leave it. Other candidates are then tried; none passing declines the order, and the ship brakes.
- **Hull test (`HullProbe`):** the box from the ship's own `CollisionShape3D`, at predicted planar poses (overlap: `intersect_shape`; sweep: `cast_motion`; both with the ship's collision mask, excluding the ship). A tick is clear when the exact hull at its first pose does not overlap (only for the first pose of a prediction; later poses lie inside the previous tick's sweep), a yaw change's hull grown by `reach · |Δyaw|` does not overlap, and that hull swept along the translation is free. So a touching ship may translate away but cannot rotate a corner inward. A segment of ticks is first tested once with the hull grown by its whole motion bound (`Σ|Δp| + reach · Σ|Δyaw|`, closing at one hull half-width); an overlap halves it down to single ticks. Conservative for geometry that is static while the plan is made; not a proof for moving bodies.
- **Validation (Task #50):** the search predicts from an anchor snapshot taken at a known physics frame. If the ship's state changed by the time a candidate passes (it only brakes meanwhile, with no order), the whole candidate is predicted again from the anchor with a predicted braking wait of 2 × (frames the search took) + 1 ticks first, doubled whenever validation itself ends after that frame. The job then **holds** the plan and hands it over exactly that many frames after the anchor, only if the ship's state equals the predicted one (`Navigator.HANDOFF_TOLERANCE`, 1e-4 summed over position, velocity, yaw and turn rate; the no-order braking is predicted exactly); otherwise the search restarts from the actual state within the same job. A holding job does no planning work, does not hold up other jobs and is handed over in the first `Navigator.service()` call of the frame, before any ship has moved. A failed validation restarts the search from the state then. (Before Task #50 only the first stretch was re-predicted, and the plan was handed over from a state the ship had already left.)
- **Guidance (per tick, real flight and prediction alike):** route progress advances past a corner when the ship crosses that corner's bisector. The pilot aims `detour_lookahead_distance` ahead along the route, the course heading follows that aim, the speed law uses the remaining path length, and each corner ahead caps the speed (step 2). Corner radius: the smaller of `lookahead / (2 sin(turn / 2))` and `(incoming + outgoing segment length) / (2 · turn)`. When the aim reaches the destination, the final approach is the ordinary direct arrival with the course frozen at the hull's yaw then (no turning left to share the thrusters with braking; no final alignment). A direct plan's course is taken from the position where the plan starts, in prediction (`ManeuverRollout`, Task #50) as at handoff (`ShipMovement`). Departures steer along their direction (zero for braking) without a course until their switch tick.
- **After handoff:** contact still ends the order under Task #44, with no retry or re-plan.

## Reusable ship composition

The reusable ship scene `Ships/ship.tscn` separates authoritative movement from a visual/model child `Visual` (a plain `Node3D` wrapper). Only that child may ever tilt visually; the authoritative root and collision never tilt.

Banking is **deferred**: Task #27 deleted the former `ShipVisualBank` script and `ShipBankProfile` resource, since they read Movement's removed API (Git history, `main` at a174d22).

Shared function and appearance use one authoritative scene/script/resource. Ship differences use configuration rather than duplicated implementations; check existing assets before creating another shared definition. Per-instance runtime state must not modify shared resources.

The owner's placeholder is `Assets/Ships/Whitebox/Arrata_Frigate_001.glb`. Preserve the source unchanged, including its scale and pivot; import metadata is asset metadata, not a movement design decision.

## Data and validation

Per-ship tuning belongs in Godot `Resource` data assets, not code constants. Shared assets hold configuration only; runtime state belongs to the individual ship. Each tunable requires a default, unit and owner-approved range. `MovementProfile` holds the provisional values (see the inventory). Start conservatively and adjust in play.

The first playable work uses one ship in open space in the developing game scene, rather than multiple test scenes. The intended battle scale is tens of units; assess it with real combat later, without treating that intention as a measured performance target.

The rejected upfront alternative is a global command/orchestration framework, an independently deployable navigation system and custom simulation. They add coupling and complexity before confirmed users require them.
